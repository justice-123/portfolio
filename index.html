Project Asphyxia — VR horror controlled by breathing

Project Asphyxia is a standalone VR horror game for Meta Quest 3 set in a hospital environment. The core mechanic turns breathing into risk: if the player breathes too loudly, a monster’s suspicion level rises; if the player stops breathing for too long, toxicity rises and hallucinations begin to distort the scene.

I worked across Unity gameplay systems, VR deployment, ML inference, audio processing, post-processing effects, and cross-scene architecture. The game is also designed around wheelchair-accessible play, avoiding mechanics that depend on standing, dodging, or room-scale movement.

3D-printed robotic pick-and-place arm

This project is a physical robotic arm built around iterative hardware testing. The system combines a NEMA 17 stepper-driven base, six MG996R servo joints through a PCA9685 servo driver, and an analytical 2-link inverse kinematics solver for reaching target positions.

The goal is to progressively add capability: first reliable joint control, then coordinate-based movement, then Pixy2 camera integration for object detection and picking. The project mixes mechanical measurement, firmware, calibration, electronics, and practical debugging.

Servo joint control

Six MG996R servos controlled through PCA9685 channels, with mirrored shoulder servos treated as one revolute joint.

How I work

Debugging from the real system backwards.

The most important lessons came from the gaps between theory, editor behaviour, hardware behaviour, and deployed builds.

01

Prototype the mechanic first

I start with the player-facing behaviour: breath raises suspicion, oxygen creates pressure, the arm reaches a target, or the gripper closes. Once the behaviour feels real, I refine the architecture underneath it.

02

Test in the target environment

For VR, that means standalone Quest builds as well as editor testing. For robotics, that means physical servo and stepper tests instead of trusting abstractions too early.

03

Prefer clear state changes

Systems are easier to debug when important state changes go through one path. Direct field writes, hidden inspector overrides, and unreliable input bindings can silently break otherwise correct code.

04

Calibrate from evidence

Whether aligning MFCC features between Python and C#, tuning servo limits, or fixing Guardian offset spawn issues, I treat mismatches as measurement problems first.
